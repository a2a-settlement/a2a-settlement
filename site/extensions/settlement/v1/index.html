Overview

A2A-SE is an A2A protocol extension implementing escrow-based settlement for agent-to-agent work. It enables agents to pay other agents for computational tasks performed (task settlement), as distinct from AP2 which enables agents to purchase goods and services on behalf of users (commerce). The two extensions are complementary and can coexist on the same agent.

ConcernAP2A2A-SE
Primary flowAgent buys product/service from merchantAgent pays agent for work completed
Economic modelCommerce (cart → payment → fulfillment)Task settlement (escrow → work → release)
Settlementx402 stablecoin / card railsToken-based escrow with exchange
Trust mechanismVerifiable Credential mandatesKYA identity + reputation scoring
Typical valueConsumer/enterprise purchasesMicrotransactions to mid-range task fees

Agent A2A-SE Roles

Every agent that supports A2A-SE MUST perform at least one role. Roles are specified in the AgentCard extension params.

RoleDescription
providerOffers skills/work for payment. Verifies escrow before executing tasks.
requesterConsumes skills from other agents. Creates escrow, releases on task completion.
bothAgent can act as both provider and requester in different interactions.

AgentCard Extension Object

Agents that support A2A-SE MUST advertise their support in their AgentCard using the Extension URI. The params field MUST adhere to the following JSON schema: 

{
  "type": "object",
  "name": "A2ASEExtensionParameters",
  "description": "Parameters for the A2A-SE settlement extension in AgentExtension.params.",
  "properties": {
    "roles": {
      "type": "array",
      "description": "The roles this agent performs in the A2A-SE model.",
      "minItems": 1,
      "items": { "enum": ["provider", "requester", "both"] }
    },
    "exchangeUrl": {
      "type": "string",
      "format": "uri",
      "description": "The settlement exchange this agent transacts through."
    },
    "accountId": {
      "type": "string",
      "description": "The agent's account identifier on the exchange."
    },
    "pricing": {
      "type": "object",
      "properties": {
        "model": {
          "type": "string",
          "enum": ["per-request", "per-token", "flat-rate", "negotiable"]
        },
        "currency": { "type": "string", "default": "ATE" },
        "skills": {
          "type": "object",
          "additionalProperties": { "type": "number" }
        }
      }
    },
    "kyaLevel": {
      "type": "integer",
      "enum": [0, 1, 2],
      "description": "Know Your Agent level. 0=sandbox, 1=organizational (did:web), 2=auditable (third-party VCs)."
    },
    "reputation": {
      "type": "object",
      "properties": {
        "score": { "type": "number", "minimum": 0, "maximum": 1 },
        "totalTransactions": { "type": "integer" }
      }
    }
  },
  "required": ["roles", "exchangeUrl"]
}

Pydantic Type Definition

from typing import Literal
from pydantic import BaseModel, Field

A2ASERole = Literal["provider", "requester", "both"]
PricingModel = Literal["per-request", "per-token", "flat-rate", "negotiable"]

class A2ASEPricing(BaseModel):
    model: PricingModel = "per-request"
    currency: str = "ATE"
    skills: dict[str, float] = Field(default_factory=dict)

class A2ASEReputation(BaseModel):
    score: float = Field(ge=0.0, le=1.0)
    total_transactions: int = Field(ge=0, alias="totalTransactions")

class A2ASEExtensionParameters(BaseModel):
    roles: list[A2ASERole] = Field(..., min_length=1)
    exchange_url: str = Field(..., alias="exchangeUrl")
    account_id: str | None = Field(None, alias="accountId")
    pricing: A2ASEPricing | None = None
    kya_level: int | None = Field(None, alias="kyaLevel", ge=0, le=2)
    reputation: A2ASEReputation | None = None

Agents that perform the "provider" role SHOULD set required: true if payment is mandatory for task execution.

Settlement Data in A2A Messages

A2A-SE uses A2A's metadata field on Messages to carry settlement context. The extensions array MUST include the A2A-SE extension URI when settlement metadata is present.

Escrow Request (Requester → Provider)

{
  "messageId": "msg-001",
  "contextId": "analysis-ctx-001",
  "role": "user",
  "parts": [
    {
      "kind": "text",
      "text": "Provide GovCon contract intelligence analysis for LDOS (Leidos Holdings)."
    }
  ],
  "extensions": [
    "https://a2a-settlement.org/extensions/settlement/v1"
  ],
  "metadata": {
    "a2a-se.escrow": {
      "escrowId": "esc-7f3a2b1c-4d5e-6f7a-8b9c-0d1e2f3a4b5c",
      "amount": 10,
      "currency": "ATE",
      "exchangeUrl": "https://exchange.a2a-settlement.org/api/v1",
      "expiresAt": "2026-02-27T04:00:00Z",
      "requesterId": "alphasignal-quant-001",
      "providerId": "eaftos-govcon-001"
    }
  }
}

Extension Negotiation

Clients activate A2A-SE by including the extension URI in the X-A2A-Extensions HTTP header:

X-A2A-Extensions: https://a2a-settlement.org/extensions/settlement/v1

If a provider agent has marked A2A-SE as required: true and the client does not activate the extension, the agent MUST return an ExtensionSupportRequiredError.

Settlement Lifecycle

The settlement lifecycle maps to A2A task states:

1. Discovery     → Client reads provider AgentCard, finds A2A-SE extension
2. Escrow        → Client creates escrow via exchange API (pre-task)
3. Task Submit   → Client sends A2A Message with escrow metadata
4. Verification  → Provider verifies escrow via exchange API
5. Execution     → Provider performs work (A2A task: working → completed)
6. Settlement    → Client releases escrow (success) or refunds (failure)
7. Reputation    → Exchange updates both agents' reputation scores

KYA (Know Your Agent) Identity

A2A-SE supports three identity verification levels that can gate escrow thresholds:

LevelIdentityVerificationEscrow Limit
0 — Sandbox API key only None Configurable (default $100)
1 — Organizational did:web bound to domain Domain TLS + self-signed card Configurable (default $10,000)
2 — Auditable did:web + third-party VCs W3C Verifiable Credentials from trusted issuers Unlimited (HITL above threshold)

KYA verification follows RFC-001: KYA-Enhanced Agent Card.

Relationship to AP2

A2A-SE and AP2 address different settlement patterns and are designed to be complementary:

  • AP2 handles commerce flows where an agent purchases goods/services from a merchant on behalf of a user. The economic model is cart-based: intent → cart → payment → fulfillment.
  • A2A-SE handles work settlement where one agent pays another agent for computational work performed. The economic model is escrow-based: discover → escrow → task → release/refund.

An agent MAY support both extensions simultaneously. For example, an orchestrator might use AP2 to purchase data from a commercial API and A2A-SE to pay a specialized analysis agent for processing that data.
